# 網站掛掉時怎麼查

這次的事故：後端**完全沒有啟動**，但瀏覽器顯示的是「已被 CORS 政策封鎖」。
先講怎麼判斷，再講這次的原因和修正。

---

## 一、三十秒判斷是哪一層壞了

打開這兩個網址（可以直接在瀏覽器貼）：

| 網址 | 有回應代表 | 沒回應代表 |
|---|---|---|
| `api.huanglong-honey.com/api/health` | **後端程式活著** | 後端沒啟動或還在部署 |
| `api.huanglong-honey.com/api/health/db` | **資料庫也正常** | 程式活著但連不到資料庫 |

`/api/health` **刻意不碰資料庫**，所以它能區分這兩件事：

```
health 有回應 + health/db 有回應   → 後端沒問題，去看前端
health 有回應 + health/db 回 503   → 資料庫的問題（訊息會告訴你要檢查哪些環境變數）
health 沒有回應                     → 後端沒起來，去看 Zeabur 的日誌
```

這次是第三種：連 `/docs` 都打不開，代表程式根本沒跑起來。

---

## 二、為什麼會顯示成 CORS 錯誤

```
Access to fetch at 'https://api.huanglong-honey.com/api/products'
from origin 'https://huanglong-honey.com' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check
```

後端沒起來的時候，Zeabur 的閘道會回一個錯誤頁。那個頁面當然不會帶
`Access-Control-Allow-Origin`，於是瀏覽器就說「被 CORS 封鎖」。

**它說的是事實，但那是結果不是原因。** 只要記住一句話：

> 看到 CORS 錯誤，先確認後端是不是還活著，不要一開始就去改 CORS 設定。

（順帶一提，「preflight」是瀏覽器在正式請求前先發的 OPTIONS 探路請求。
因為我們的請求會帶 `Authorization` 標頭，所以每一支 API 都會先來一次 preflight。）

---

## 三、這次的真正原因

上一版加了「啟動時自動把太窄的欄位加寬」的功能。原本寫成這樣：

```python
@app.on_event("startup")
async def on_startup():
    ensure_database()
    Base.metadata.create_all(bind=engine)
    sync_schema()          # ← 這裡面有一句 ALTER 失敗
```

`sync_schema()` 把所有 `ALTER TABLE` 包在同一個交易裡執行。
只要有一句失敗，例外就一路往上拋 → startup 事件失敗 → **uvicorn 判定啟動失敗直接結束** →
容器不斷重啟 → 所有請求都失敗。

**調整欄位寬度這種小事，不該有能力讓整個網站下線。** 這是設計上的錯，已經改掉。

---

## 四、改了什麼

### 1. 每一句 ALTER 各自獨立、各自防護

```
[資料表更新] news.source_url 加寬為 TEXT
[資料表更新] 失敗：products.image_url 加寬為 TEXT
  SQL: ALTER TABLE `products` MODIFY `image_url` TEXT NULL
  原因: (1170, "BLOB/TEXT column used in key specification without a key length")
[資料表更新] 完成 7 項，失敗 1 項（詳見上方日誌，網站仍可正常啟動）
```

一句失敗就記錄下來、跳過、繼續下一句。網站照樣起來。

順便也改成一句一個交易 —— MySQL 的 DDL 本來就不能回滾，
包在一起只會讓「前面成功、中間失敗」更難收拾。

### 2. 加寬前會問資料庫實際有哪些索引

MySQL 不允許把有索引的欄位改成 TEXT（就是上面那個 1170 錯誤）。
原本只看程式裡的模型宣告，但資料庫裡可能有模型沒宣告的索引
（早期手動加的、或外鍵自動建的）。現在會直接問資料庫：

```python
indexed_columns(inspector, table)   # 含索引、主鍵、外鍵
```

讀不到索引資訊時保守處理 —— 寧可不改，也不要下一句會失敗的 ALTER。

### 3. 資料庫沒好不會讓網站起不來，而且會自己恢復

```
[啟動] 蜂蜜商城 API 啟動中．環境 =production．允許的來源 =['https://huanglong-honey.com']
[啟動] HTTP 服務已就緒（資料庫在背景初始化）
[啟動] 資料庫初始化失敗（第 1 次）：OperationalError: (2003, "Can't connect to MySQL server...")
[啟動] 資料庫初始化完成（第 2 次嘗試）
```

HTTP 服務**先起來**，資料庫在背景初始化，失敗就每 15 秒重試（啟動時最多等 90 秒，
之後改成每分鐘慢慢試）。

這在 Zeabur 上很重要：**應用常常比資料庫先啟動**。
第一次連不上是很正常的事，那不該是永久性的死亡。
資料庫回來之後系統會自己好，不需要人工重啟。

### 4. 資料庫沒好的時候，API 回的是看得懂的 503

```json
{ "detail": "資料庫暫時連不上，請稍後再試。如果一直這樣，請確認資料庫服務是否還在運作。" }
```

而且**帶 CORS 標頭**，所以瀏覽器看得到這句話，不會又變成 CORS 錯誤。

### 5. 前台的錯誤訊息會告訴你去看哪裡

以前只說「無法連線到伺服器，請稍後再試」。現在：

> 無法連線到伺服器。可能是後端服務沒有啟動，或資料庫連不上。
> 可以打開 `https://api.huanglong-honey.com/api/health` 確認：有回應代表程式活著，
> 再看 `/api/health/db` 確認資料庫。

### 6. 啟動階段的日誌一定看得到

加了 `logging.basicConfig` —— uvicorn 只設定它自己的 logger，
root logger 預設沒有 handler，所以我們自己寫的訊息以前**會全部消失**，出事時毫無線索。
最關鍵的幾行改用 `print(flush=True)`，不管 logging 怎麼設定都會進到平台日誌。

### 7. 上傳資料夾建不出來也不會致命

`UPLOAD_DIR.mkdir()` 是在 import 階段跑的，拋例外容器會直接死掉。
現在建不出來只記錄並跳過掛載 —— 上傳功能壞掉遠好過整站掛掉。

## 五、現在該做什麼

1. **把這一版推上去並重新部署**
2. 打開 `api.huanglong-honey.com/api/health` —— 應該會看到 `{"status":"ok"}`
3. 打開 `api.huanglong-honey.com/api/health/db` —— 確認資料庫
4. 到 Zeabur 看後端服務的日誌，找 `[啟動]` 和 `[資料表更新]` 開頭的幾行

如果 `/api/health/db` 回 503，訊息會告訴你要檢查這四個環境變數：
`DB_HOST`、`DB_USER`、`DB_PASSWORD`、`DB_NAME`。

如果 `[資料表更新]` 有失敗的項目，把那幾行貼給我，我看 SQL 就知道是什麼問題。
**網站會照常運作**，只是那個欄位還是舊的寬度。

---

## 六、Zeabur 上怎麼看日誌

後端服務 → 選到執行中的那個 instance → **Logs**。

值得注意的關鍵字：

| 看到什麼 | 意思 |
|---|---|
| `[啟動] HTTP 服務已就緒` | 程式起來了 |
| `[啟動] 資料庫初始化完成` | 一切正常 |
| `[啟動] 資料庫初始化失敗` | 看後面的錯誤，通常是環境變數或資料庫沒開 |
| `[資料表更新] 失敗：` | 某一句 ALTER 沒過，網站仍可運作 |
| `Application startup failed` | **不該再出現了**，如果出現請把整段貼給我 |
| 完全沒有 `[啟動]` 開頭的行 | 連 import 都沒過，看更上面的 Traceback |

## 七、測試

```
cd backend && python tests/test_startup_resilience.py
```

35 項，全部針對「壞掉的時候會怎樣」：

- 單句 ALTER 失敗時 `sync_schema()` 不拋例外
- 完全連不上資料庫時 `sync_schema()` 安靜收場
- 資料庫連不上時 `/api/health` 仍回 200、`/api/health/db` 回 503
- 資料庫連不上時 API 回**帶 CORS 標頭**的 503，不是讓瀏覽器看到 CORS 錯誤
- **OPTIONS 預檢在資料庫掛掉時仍要通過**（不然瀏覽器連錯誤內容都拿不到）
- 有索引的欄位不會被改成 TEXT；讀不到索引資訊時保守不改
- 資料庫正常時一切行為照舊
