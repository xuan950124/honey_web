# 存檔失敗的排錯記錄（長網址造成的 500）

留這份是因為排錯的過程本身有價值 ——
畫面上顯示的錯誤和真正的原因完全是兩件事。

---

## 一、你看到的

後台新聞管理按「儲存變更」，畫面顯示：

> 無法連線到伺服器，請稍後再試

開發者工具的主控台裡是這些：

```
POST https://api.huanglong-honey.com/api/news  net::ERR_FAILED 500 (Internal Server Error)
Access to fetch at 'https://api.huanglong-honey.com/api/news' from origin
'https://huanglong-honey.com' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

看起來像跨網域（CORS）設定壞了。**不是。**

---

## 二、真正的原因

你貼進「原文連結」的那條 Facebook 網址有 **753 個字元**。

Facebook 會把整篇貼文的標題做 URL 編碼塞進路徑裡，一個中文字變成 9 個字元：

```
歡  →  %E6%AD%A1
```

那條網址的資料庫欄位原本設成 `VARCHAR(400)`，753 > 400，
MySQL 直接拒絕寫入並丟出 `Data too long for column 'source_url'`，
FastAPI 沒接住就變成 500。

## 三、為什麼看起來像 CORS 問題

這是最值得記下來的一段。

Starlette（FastAPI 底層）的請求處理是一層包一層的：

```
ServerErrorMiddleware   ← 最外層，負責把沒人接的例外變成 500
  └─ CORSMiddleware      ← 負責加上 Access-Control-Allow-Origin
      └─ ExceptionMiddleware
          └─ 你的路由
```

錯誤在最裡面發生，一路往外拋，**在 CORSMiddleware 還沒來得及加標頭之前**
就被最外層的 ServerErrorMiddleware 接走變成 500 回應了。

那個回應沒有 `Access-Control-Allow-Origin`，於是瀏覽器看到跨網域的回應少了標頭，
就報「已被 CORS 政策封鎖」—— 它說的是事實，但那是**結果**，不是**原因**。

真正的原因（網址太長）被完全蓋掉了。

---

## 四、改了什麼

### 1. 存網址的欄位一律改成 TEXT

社群平台的網址長度沒有上限可言，設任何 `VARCHAR(N)` 都只是等下一次踩雷。

| 欄位 | 原本 | 現在 |
|---|---|---|
| `news.source_url` | VARCHAR(400) | **TEXT** |
| `news.cover_url` | VARCHAR(255) | **TEXT** |
| `stories.cover_url` | VARCHAR(255) | **TEXT** |
| `products.image_url` | VARCHAR(255) | **TEXT** |
| `product_images.image_url` | VARCHAR(255) | **TEXT** |
| `news.title` | VARCHAR(200) | VARCHAR(300) |
| `news.summary` | VARCHAR(300) | VARCHAR(600) |
| `stories.title` / `subtitle` | VARCHAR(200) | VARCHAR(300) |

### 2. 程式啟動時會自動把欄位加寬

原本的 `sync_schema()` 只會「新增缺少的欄位」，不會改既有欄位的型別，
所以光改程式不會生效。現在它也會把**太窄的欄位加寬**。

兩個刻意的限制：

- **只加寬，永遠不縮小。** 縮小會截斷既有資料，那是不可逆的。
  就算之後把模型改小了也不動 —— 寧可資料庫比程式寬鬆
- **有索引或唯一約束的欄位不動。** 把 `users.email` 改成 TEXT 會讓 MySQL
  抱怨索引長度，那類欄位本來也不會存長網址

> **你需要做的事：重新部署一次後端**（Zeabur 上重新 Redeploy 即可）。
> 啟動時會自動執行 `ALTER TABLE`，日誌會印出
> `[資料表更新] news.source_url 加寬為 TEXT`。之後就能存那條網址了。

### 3. 錯誤訊息不再說謊

加了一層 middleware 把所有沒接住的例外變成帶 CORS 標頭的中文 JSON。
關鍵是**寫成 middleware 而不是 `@app.exception_handler(Exception)`** ——
後者是交給最外層的 ServerErrorMiddleware，還是拿不到 CORS 標頭。

寫成 middleware 並宣告在 CORS 之前，CORS 就會包在外面（後加的在最外層）。

現在同樣的情況會顯示：

> 「原文連結」的內容太長，資料庫存不下。如果是很長的社群網址，
> 請重新啟動一次後端讓資料表自動加寬，或改貼短一點的連結。

其他常見的資料庫錯誤也一併翻譯了：

| 情況 | 狀態碼 | 訊息 |
|---|---|---|
| 內容太長 | 400 | 指名是哪個欄位太長，並說明怎麼處理 |
| 資料重複 | 400 | 這筆資料和現有的重複了（例如 Email 已被使用）|
| 關聯資料不存在 | 400 | 關聯的資料不存在或已被刪除，請重新整理 |
| 資料庫連不上 | 503 | 資料庫暫時連不上，請稍後再試 |
| 其他 | 500 | 附上例外的類型名稱，方便對照日誌 |

訊息一律不外洩 SQL 語句。

### 4. 後台先擋，不要讓伺服器噴錯

標題、摘要、報導媒體這幾個還是 `VARCHAR` 的欄位，
在**送出前**就會檢查長度並列出哪一欄超過多少。
接近上限（80%）時欄位標籤旁邊會出現字數，平常不顯示，不干擾。

原文連結下方直接寫明「長度沒有限制，Facebook 那種超長網址直接整條貼上就可以」。

## 五、順便說：主控台裡那一堆 M_ID 錯誤不是網站的問題

```
Uncaught (in promise) TypeError: Cannot read properties of undefined (reading 'M_ID')
    at Z (200.js:1:761)
```

滑鼠移過去會看到來源是：

```
chrome-extension://eppiocemhmnlbhjplcgkofciiegomcon/executors/200.js
```

`chrome-extension://` 開頭代表這是**瀏覽器擴充功能**在報錯，不是我們的程式碼。
數量看起來很多是因為它會反覆重試。

可以不用管它。如果覺得吵，開一個無痕視窗（擴充功能預設不啟用）再看主控台，
畫面會乾淨很多，也比較容易看出哪些錯誤是真的要處理的。

同理，`MaxListenersExceededWarning` 和 `ObjectMultiplex - orphaned data`
也是來自 `contentscript.js`，同樣是擴充功能。

## 六、測試

```
cd backend && python tests/test_long_urls.py
```

84 項，包含：

- 用**使用者實際貼的那條 753 字元網址**存進去、更新、再存 2000 字元
- 欄位加寬的判斷：該加寬的要加寬、已經夠寬的不動、**絕對不會縮小**、有索引的不碰
- 實際產生的 `ALTER TABLE` SQL 字串（沙箱裡沒有 MySQL，但 SQL 文字本身最容易寫錯）
- 錯誤回應**確實帶有 CORS 標頭**、是 JSON、有中文說明、不外洩 SQL
- 正常請求與 404 的行為沒有被改掉
