# 安全性檢視與修正

依外部 review 的建議做的一輪修正。這份記錄改了什麼、為什麼，以及**還沒做的部分**。

---

## 一、最嚴重的一個：別人可以看到你客人的訂單

### 問題

訂單編號長這樣：

```
20260818124533712
└─ 年月日時分秒 ─┘└┬┘
                隨機三位數
```

前 14 碼是時間戳，看得出規律；只有最後三碼是隨機的。
而查訂單的 API **完全不需要登入**：

```
GET /api/orders/by-no/20260818124533712
```

也就是說，只要用程式跑過某個時段的所有組合（一秒 1000 種），
就能撈出那段時間所有訂單的**收件人姓名、電話、地址、購買品項**。
這是個資外洩，不是小事。

### 修正

每筆訂單多一組隨機存取碼（`secrets.token_urlsafe(16)`，22 個字元）。
查訂單要滿足三者之一：

1. 工作人員登入
2. 訂單本人登入
3. 網址帶對存取碼

訪客沒有帳號，靠的是第 3 種 —— 付款完成後導回的網址會帶著那組碼：

```
/order/20260818124533712?t=xK3p9vQ2mNbL7wRzYtA8Hg
```

**找不到訂單和沒有權限一律回同一句話。** 回「無權查看」等於承認這個編號存在，
那就變成可以拿來確認有哪些訂單，等於沒修。

付款頁（`/api/payments/{order_no}/checkout`）也一併要求存取碼 ——
那一頁上面會顯示金額與商品明細。

> 舊訂單沒有存取碼，系統啟動時會自動補上，日誌會印
> `[啟動] 已為 N 筆舊訂單補上存取碼`。

## 二、兩個人同時買最後一組，會兩個都成立

### 問題

原本是「先讀庫存 → 判斷夠不夠 → 扣掉」。兩個請求同時進來時：

```
A 讀到庫存 1  →  夠  ─┐
B 讀到庫存 1  →  夠  ─┴→  兩筆訂單都成立，庫存變成 -1
```

網路上訂單一多就會發生，然後你得跟其中一個客人道歉。

### 修正

下單時用 `SELECT ... FOR UPDATE` 把商品那幾列鎖住，直到訂單 commit 才放開。
B 會停在「讀」那一步等 A 做完，讀到的就是扣完之後的數字，於是被正確擋下。

另外**依商品 ID 排序再鎖**。兩筆訂單買同樣兩件商品但順序相反時，
沒排序會 A 鎖住甲等乙、B 鎖住乙等甲，互相等到天荒地老（死鎖）。

順帶修掉一個繞過方式：同一個商品送成兩行（各 3 組），
原本會分別通過「庫存 5 夠不夠」的檢查。現在先合併成 6 再檢查。

## 三、付款成功以哪一個通知為準

綠界有兩條回傳路徑：

| 路徑 | 走法 | 可信度 |
|---|---|---|
| `ReturnURL` | 綠界伺服器 → 我們伺服器 | **高**，中間沒有使用者 |
| `OrderResultURL` | 綠界 → 使用者瀏覽器 → 我們 | 低，內容經過使用者的機器 |

原本兩條都會把訂單標成「已付款」。雖然兩條都有驗 `CheckMacValue`（沒有金鑰算不出來），
但原則上**不該讓經過使用者機器的資料決定錢有沒有收到**。

現在 `OrderResultURL` 只做兩件事：記錄一筆日誌、把人導回訂單頁。
真正的判定改成**主動打綠界的 QueryTradeInfo 問一次** —— 那也是伺服器對伺服器。

兩條路徑都會核對金額，對不上就拒絕並記錄，不會自動標成已付款。

## 四、連續猜密碼

原本登入 API 沒有任何次數限制，拿一份常見密碼清單就能慢慢試。

現在連續失敗 5 次會鎖 15 分鐘，**同時看帳號和來源 IP**：

- 只看帳號 → 攻擊者換帳號繼續猜，而且可以故意鎖死別人的帳號
- 只看 IP → 同一間辦公室的人會互相影響

剩 2 次以下時會提示「還可以再試 N 次」，被鎖時提示可以改用「忘記密碼」。

> 計數存在記憶體裡，重啟會歸零、多個容器各算各的。
> 對這個規模夠用 —— 要擋的是自動化腳本，而腳本不會因為我們重啟就重來。
> 之後要更嚴謹再換成 Redis。

## 五、上傳檔案

原本只看副檔名。副檔名是使用者自己取的，把 HTML 或 SVG 改名成 `.jpg` 一樣傳得上來。

現在加了三道：

1. **驗檔案開頭的魔術位元組** —— JPG 是 `FF D8 FF`、PNG 是 `89 50 4E 47`…
   內容對不上就擋，並提示「請用看圖軟體另存成真正的 JPG／PNG」
2. **不收 SVG** —— SVG 是 XML，裡面可以放 `<script>`，
   被當成圖片開啟時會執行，是典型的儲存型 XSS 管道
3. **檔名一律重新產生**（uuid）—— 用原始檔名的話，
   別人可以用 `../../` 跳出上傳資料夾，或用同名檔覆蓋別人的圖

另外加了安全標頭，`/uploads` 底下的檔案一律 `Content-Security-Policy: default-src 'none'; sandbox`
和 `X-Content-Type-Options: nosniff`，就算真的傳上去奇怪的東西也不會被當成網頁執行。

## 六、金額重算（原本就是對的）

review 提到「金額一定要後端重算」—— 這一點原本就已經做到了，測試也釘住了：

`OrderCreate` 這個下單格式**根本沒有價格欄位**。前端只能傳商品 ID 與數量，
價格、運費、會員折扣、折價券折抵全部是後端自己查、自己算。
就算有人改請求也改不到金額。

測試會檢查 `total_amount`、`subtotal`、`price`、`shipping_fee`… 這些名字
都不在下單格式裡 —— 之後如果有人不小心加進去，測試會馬上失敗。

## 七、前台不該出現的字

三處「給自己人看的話」漏到客人眼前：

| 位置 | 原本 | 現在 |
|---|---|---|
| 品牌故事結尾 | 「（這段文字可於後台「故事管理」自行修改）」| 顯示前自動濾掉 |
| 聯絡頁社群欄 | 「（待補上）」| 沒填的欄位對客人**整列隱藏** |
| 聯絡頁底部 | 「以上聯絡資訊由工作人員於後台維護」| 只有工作人員看得到 |

商品照片的檔名提示（`product-5.jpg`）也一樣 —— 那是給你對照用的，
客人現在看到的是「照片準備中」，或乾脆留白。
商品內頁沒有其他照片時，那排四個空框整個不顯示。

另外圖片載入失敗時會退回留白，不再出現破圖圖示；
工作人員會看到紅字的「圖片載入失敗」與網址，方便修。

## 八、上線前的提醒放進後台

後台總覽最上面現在會出現兩種警告：

- **綠界還是測試環境** —— 客人的付款不會真的入帳。
  告訴你要把 `ECPAY_ENV` 設成 `production` 並填正式金鑰
- **有 N 個上架商品沒有主圖** —— 直接列出商品名稱，點一下就去編輯

這兩件事都屬於「網站看起來正常、但實際上會出事」，
所以放在第一眼看得到的地方，而不是等人自己想起來。

## 九、還沒做的（依 review 的建議）

### 法規面（下一輪）

- 隱私權政策、服務條款、退換貨政策三個頁面與頁尾連結
- 商品頁的食品標示欄位：內容物、淨重、原產地、保存期限、營養標示、過敏原、廠商資訊
- **一歲以下嬰兒不宜食用**的警語（肉毒桿菌孢子風險）
- 食品業者登錄字號與統一編號放頁尾

> 退換貨那一項有個時間點的問題：食品可以依「通訊交易解除權合理例外情事適用準則」
> 排除七天猶豫期，但**必須在消費者下單前明確告知**，沒寫就不能排除。
> 這件事越早補越好。

### SEO（先不動架構）

sitemap、結構化資料、og 標籤這些可以隨時補。
但「爬蟲讀不到內文」要導入 SSR 或預渲染，那是換前端架構的等級，另外評估。

### 營運面（不是程式能解決的）

- 每日備份訂單與會員資料，**而且要真的演練還原一次**
- 錯誤監控（Sentry）與 uptime 監控
- 貨到付款的棄件風險：可以設首購金額上限
- 檢驗報告（農藥、抗生素、水分、HMF）—— review 說得對，
  這比任何文案都有說服力
- Email 改用 `service@huanglong-honey.com` 取代 gmail

## 十、測試

```
cd backend && python tests/test_security.py
```

95 項，全部是**攻擊者視角**：不是驗證正常流程能跑，而是驗證不該成功的事真的失敗了。

- 用猜的訂單編號打 API → 404，而且回應裡**沒有姓名、電話、地址**
- 存取碼錯一個字元、短一半、多一個字元 → 都擋
- 連續猜密碼 → 第 5 次被鎖，**鎖定期間連正確密碼也進不去**
- HTML／SVG／PHP 改名成 `.jpg` `.png` `.gif` → 都擋
- 一般會員呼叫上傳 API → 403
- 下單格式裡不存在任何價格欄位
- 瀏覽器導回的路徑不會寫入付款結果
